~~~python
from benchagent.job_manager import JobManager

manager = JobManager().start()
# 已明确确认的计划才可提交；此调用会创建排队任务并由后台执行。
receipt = manager.submit_plan(plan_id, digest, execution_request_id, confirmation_id)
job = manager.get_job_snapshot(receipt["job_id"], after_seq=0)
# 需要取消时显式调用，回执并不表示进程已经退出。
cancel = manager.cancel_job(receipt["job_id"], cancel_request_id)
# 关闭时会请求当前任务取消并等待清理；False表示尚未清理完，所有权记录仍保留。
closed = manager.close(timeout=15)
~~~

服务构造和快照查询不启动任务；start启动工作器，但不会自动重放旧队列。
同一 execution-submit 请求和计划返回相同job_id，不再启动第二次；改绑计划返回REQUEST_CONFLICT。
提交前同时核对确认、草稿版本、计划摘要及实际文件身份。
任务接受后使用自己的不可变快照，后续编辑草稿不会改变已接受参数。

## 状态与持久化

job-v1保存在data/planning/state.json的jobs中，submissions和cancel_requests与任务在同一原子替换中提交。
事件嵌入每个任务的events，seq严格递增；get_job_snapshot(after_seq)只过滤返回事件，不推进执行。
本阶段采用同一原子状态文件，尚未拆成job_state.json和events.jsonl，避免跨文件半登记。

COMPLETED表示调度和报告结束，result_status才是校验结论，允许COMPLETED加FAIL。
运行中主动取消为CANCELLED，已启动用例记录FAIL及failure_kind=CANCELLED，后续未启动项为SKIPPED。
排队/准备阶段取消不创建仿真进程。最后用例已进入解析或归档时返回FINALIZING，完成必要归档。
取消请求不覆盖既有成功用例。报告写入失败时不发布成功引用或结果状态。

服务实例用data/planning/.manager.lock防止重复工作器。
成功取得管理所有权后，遗留非终态任务标为INTERRUPTED，不自动续跑或重新提交。
进程崩溃留下的管理写锁、元数据写锁、执行锁均不自动抢占；须先核查归属，不能以PID、TTL或日志停滞直接接管。
已知清理失败会阻止队列继续。生命周期与进程归属情况都保留在快照中。

## 进程树与租约

Windows用CREATE_SUSPENDED创建根进程，绑定自己的Job Object后恢复主线程，避免解释器启动器或快速子进程在绑定前逃出追踪。
结束时确认Job Object活动进程数为零，再清空child_pid及释放execution-lease-v1。
租约含owner_token、owner_pid、job_id、取得时间和child_pid。释放需匹配自身令牌；旧PID锁一律视为占用。
超时与取消只处理本任务的Job Object，不按进程名终止其他程序。
无法确认清理时保留锁，任务FAILED且failure_kind=CLEANUP_REQUIRED，后续不启动。

真实辅助检查显式创建后代，活动进程数由4降至0，确认退出后才释放锁：
[进程树实测](BG03_进程树实测.json)。
