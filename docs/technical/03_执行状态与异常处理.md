# 03 执行状态与异常处理

## 1. 三类状态分开

| 状态层 | 枚举/内容 | 说明 |
|---|---|---|
| 任务集状态 job.state | QUEUED、ACTIVE、CANCELLING、COMPLETED、CANCELLED、FAILED、INTERRUPTED | 工作流是否仍在处理 |
| 子任务阶段 case.phase | PENDING、PREFLIGHT、PREPARING、RUNNING、PARSING、VALIDATING、REPORTING、COMPLETED、SKIPPED、CANCELLED、FAILED | 当前用例推进到哪里 |
| 校验结论 result_status | PASS、FAIL、PARTIAL、SKIPPED；未产生结果前为 null | 继续沿用确定性规则 |

COMPLETED 不等于 PASS；可以出现任务集已结束但部分用例校验失败。
取消不能伪装成 PASS；QUEUED、合成演示和没有任务的页面不能出现真实结果结论。
字段命名在正式 Schema 中保持明确，不以一个 status 混装三个概念。

## 2. 右侧六步流程映射

| 原型阶段 | 事实依据 |
|---|---|
| 任务解析 | 已验证并冻结计划；此时还没有子进程 |
| 环境检查 | 当前子任务 PREFLIGHT 的检查事件 |
| 配置参数 | PREPARING：计划快照、环境覆盖策略、独立目录准备 |
| 运行仿真 | RUNNING：子进程已创建，完整 CSV 行更新帧进度 |
| 数据分析 | PARSING / VALIDATING：进程结束后解析和确定性检查 |
| 生成报告 | REPORTING：报告及清单写入、提交可读引用 |

阶段条显示当前 case_id 的阶段，父任务另显示“第几项 / 共几项”。
切换下一个用例时以新 case_id 重置阶段条；不让同一用例在没有解释的情况下倒退。
计划解析结果可被各子任务复用，不为每个用例重复调用模型。
合成模式中的紫色流程只是示意，不能写入真实任务事件。

## 3. 正常流程

~~~mermaid
stateDiagram-v2
    [*] --> QUEUED
    QUEUED --> ACTIVE: 工作器取得执行租约
    ACTIVE --> COMPLETED: 子任务处理与汇总归档结束
    QUEUED --> CANCELLED: 未启动前取消
    ACTIVE --> CANCELLING: 请求取消
    CANCELLING --> CANCELLED: 自有进程确认结束并归档
    CANCELLING --> FAILED: 无法完成清理
    ACTIVE --> FAILED: 系统级异常无法继续
    ACTIVE --> INTERRUPTED: 服务意外中断后对账
~~~

每个活动子任务依次执行 PREFLIGHT → PREPARING → RUNNING → PARSING →
VALIDATING → REPORTING → COMPLETED。
单项程序退出异常可以产生 FAIL 报告；父任务按固定策略继续其他独立用例。
运行身份发生变化或无法确认进程结束等全局问题必须停止后续启动。

## 4. 工作器与执行锁

- 一个服务实例一个串行工作器；每次只处理一个任务集。
- 同工作区的 UI 与 CLI 共用执行租约，跨进程同样不能并发。
- 当前 runs/.execution.lock 的独占创建策略保留兼容，内部所有权需扩展。
- 锁记录至少包含 owner_token、owner_pid、job_id、取得时间、已登记的 child_pid。
- 释放只允许匹配自身 owner_token；不能由 UI 根据文件存在就删除。
- 旧版只记录 PID 的锁按 legacy 占用处理，不自动猜测其归属。
- 同一任务集在整个子任务运行、证据归档和后置身份核对完成前保有租约。
- 多用例不嵌套调用含锁的旧 execute；运行器内部接收已取得的租约上下文。
- 取消/超时的 finally 不能无条件删除锁；必须先有进程结束确认。
- TTL 或“很久没有日志”不能作为删除锁、杀死进程或启动下个任务的唯一依据。

已有锁无法证明安全释放时，队列保持阻塞并显示需要核查，不自动接管不明进程。

## 5. 取消协议

| 时机 | 行为 |
|---|---|
| 排队中 | 标记取消，所有尚未启动用例为 SKIPPED，不创建子进程 |
| 正在准备但尚未启动 | 再检查取消令牌，停止启动并归档已取得的准备证据 |
| 进程运行中 | 进入 CANCELLING，只终止本任务持有并核实归属的进程树 |
| 正在解析/报告 | 完成当前用例的必要校验/归档后停止后续用例；已完成结论保留。最后一项无后续可取消时返回 FINALIZING，不中断归档或伪称已取消 |
| 已终态 | 返回幂等终态，不回写为取消，也不重新执行 |

取消 API 返回“已收到请求”不表示进程已经结束。
若全部用例已结束并进入最后归档，不能把成功记录追认为一次取消；返回正在收尾或已终态。
运行中的取消流程：请求登记 → 阻止后续启动 → 终止自有进程树 →
等待并核对退出 → 刷新/关闭日志 → 归档取消信息与检查清单 → 释放租约。
实际执行过但被中断的用例记录 FAIL 与 failure_kind=CANCELLED；
未启动用例为 SKIPPED；job.state=CANCELLED。

若无法确认清理成功，记录 CLEANUP_REQUIRED，保留租约，job.state=FAILED，
阻止后续任务。不能在界面上显示“已取消”并继续运行下一项。

## 6. 超时、失败和中断

| 分类 | 证据与处理 | 对后续用例 |
|---|---|---|
| ENV_UNAVAILABLE | 前置检查不足，不启动；单项 SKIPPED | 同一全局原因则后续也跳过 |
| LAUNCH_FAILED | 进程创建失败，保存异常与命令身份 | 判断全局原因后决定是否继续 |
| PROCESS_EXIT | 非零退出码、日志、可用部分证据 | 确认清理与身份稳定后可继续 |
| TIMEOUT | 运行超时、进程树终止确认、部分证据 | 清理成功后可继续 |
| EVIDENCE_INVALID | 文件缺失/损坏、错误帧数、非有限值或检查不符 | 保留 FAIL，不掩盖；可继续独立用例 |
| CANCELLED | 取消请求、结束确认、未启动用例清单 | 不启动后续用例 |
| CLEANUP_REQUIRED | 无法确认进程结束或所有权异常 | 保留锁，停止队列 |
| INTERRUPTED | 服务异常重启发现遗留活动任务 | 恢复视图，不自动续跑物理进程 |

BG-03已区分CANCELLED、CLEANUP_REQUIRED、IDENTITY_CHANGED等类别；旧记录的failure_kind保留原始值，
由视图层附加映射，不修改旧 report.json。

单项超时只衡量进程运行的安全上限，不作为性能合格线。
等待租约的时间与仿真进程墙钟时间分别记录。
服务重启后不能仅凭 PID 相同就认领进程；PID 可能被复用，应结合原记录与所有权材料。
没有足够材料时标 interrupted/需核查，不自动恢复求解或终止不明 PID。

## 7. 进度读取

- 当前原生程序每帧 flush frames.csv，进度读取器只接受完整换行、字段可读且连续的帧。
- 绑定 job_id、case_id 和本次独立 raw 路径；不能读取上次路径或只看全局最新文件。
- 半行保留到下次，不计入进度，不改写原始文件。
- 重复、回退、乱序或超目标记录形成遥测异常，不能偷偷修正后当正常完成。
- 完成一帧的进度信息不等于该帧或整个任务通过最终校验。
- 进程存活期间不调用要求终态文件齐全的最终解析/验证流程。
- ETA 没有足够样本时为 null；有值时标估算，不参与验证器判定。
- UI 更新节流并记录策略；不新增 GPU 同步或阶段剖析来驱动进度条。

标准套件目标总帧数为 170；子集为对应目标帧数之和。
正常运行显示已确认帧数/目标帧数；失败/取消后保持实际值，不能因结束而补成 100%。

## 8. 持久化与发布顺序

BG-03当前在data/planning/state.json中原子保存任务快照和嵌入events数组，seq在同一job内严格递增。
原规划的job_state.json及events.jsonl暂不拆分；后续流式读适配须保留原标识与序号。
事件包含 job_id、case_id、plan_id、seq、UTC 时间、事件类型与观测摘要。
UI 以 seq 判断快照新旧，不能只按墙上时间排序。

报告发布顺序：

1. 保留原始证据和退出信息。
2. 写入 run_meta、指标和 checks。
3. 生成报告，提交报告引用。
4. 更新最终状态与可下载产物清单。

报告写入失败不能先宣布完整成功；保留错误并标注 REPORTING 未完成。
事件截断或索引损坏时以可核查的任务文件恢复视图，不能据此自动重跑。
