# 02 数据模型与服务接口

本文件定义目标应用契约；BG-01 归档视图和 BG-02 对话/草稿/计划/确认已实现库层。
BG-03异步任务、提交和取消已实现；BG-04 AppService/六导航界面已接入。历史机器证据保持不变。
[返回总纲](README.md)。

## 1. 标识与关联

~~~text
conversation_id
  └─ message_id / draft_id + revision
       └─ plan_id + plan_digest（冻结快照）
            └─ request_id → job_id（幂等提交）
                 ├─ case_id（20/50/100 帧子任务）
                 └─ report_id（任务集或单项报告）
~~~

| 对象 | 关键字段 | 必须满足的规则 |
|---|---|---|
| 对话 | conversation_id、messages、active_draft_id | 记录需求及来源，不是任务执行状态源 |
| 消息 | message_id、actor、content、source_kind、request_id | actor 区分 user/rule/model/system，规则文本不伪装模型回复 |
| 草稿 | draft_id、revision、conversation_id、task_request、origin | 可修改；每次实质修改增加 revision |
| 冻结计划 | plan_id、draft_id、draft_revision、plan_digest、execution_snapshot | 预览生成后不可修改；提交才记录用户确认 |
| 提交索引 | request_id、plan_id、plan_digest、job_id | 相同提交可重试；冲突不能覆盖原任务 |
| 任务 | job_id、plan_id、state、result_status、cases、owner、timestamps | 生命周期与校验结论分开 |
| 子任务 | case_id、frames、phase、confirmed_frames、artifacts、result_status | 帧数白名单；每项独立从初态启动 |
| 报告引用 | report_id、job_id、case_id、source_kind、relative_paths | 通过仓库查找，不把 ID 当任意文件路径 |
| 视图快照 | context、selection、data_source、metrics、checks、progress、logs | 身份一致后才显示为同一任务的结果 |

request_id 按操作命名空间区分：task_request 中的是意图追踪标识，
submit_plan 中的是执行提交的幂等标识，模型调用另有独立请求标识。
执行提交索引使用 execution-submit 命名空间，不把消息重试或模型回复当成执行重试。
这些标识通过草稿/计划关联，不因字段同名就自动视为一次执行确认。

ID 由服务生成或验证，不能使用用户输入的任意目录名。
源文件中的相对路径只作为受控记录字段，解析后仍须位于允许目录内。

## 2. 受限任务请求

现有设计契约：[task_request_v1.schema.json](../contracts/task_request_v1.schema.json)。
正式接入时在服务边界执行 Schema 和语义校验，不依赖按钮禁用状态。

~~~json
{
  "schema_version": "task-request-v1",
  "request_id": "example-plan-request-001",
  "mode": "custom",
  "scene": "default",
  "backend_id": "c0-003-benchagent-v1",
  "task_frames": [100],
  "timeout_sec": 3600
}
~~~

约束：

- 标准模式为 [20,50,100] 全三项；自定义为白名单非空、无重复子集。
- 校验通过后按固定用例顺序执行，不因输入顺序改变基准协议。
- timeout_sec 是 1–86400 的整数秒；不接受布尔值冒充整数。
- 不接受场景切换、自由帧数、dt/摩擦/容差覆盖、可执行文件或任意命令字段。
- 当前 CLI 的 run / bench 计划保留兼容；不直接把新 UI 请求传给旧 validate_plan。
- 适配器负责单项、全套和子集的统一调度，不能由页面循环嵌套调用 execute。

## 3. 草稿与冻结计划

草稿只持有意图及固定白名单参数。计划服务在预览时读取本地身份，形成不可变 ExecutionPlan。
预览生成快照不代表用户已确认；明确点击开始执行并提交后才记录 confirmed_at。执行快照包括：

| 执行快照字段 | 内容 |
|---|---|
| request | 规范化后的任务请求 |
| source_identity | 基线提交、共用实现、观测适配版本、源码清单及输入哈希 |
| runtime_identity | 运行清单哈希、EXE/DLL 哈希、固定可执行文件位置 |
| profile_identity | C0 配置标识、配置哈希、固定 GPU 选择 |
| environment_policy | 清除继承覆盖变量、固定工作目录、受控 PATH |
| protection | 每项超时及既定诊断保护，不改变收敛阈值 |
| provenance | 草稿版本、生成来源、生成时间；确认时间记录在提交记录中 |

plan_digest 只对规范化执行快照计算，不包含自身、不包含可变 UI 状态。
建议固定算法：JSON 键排序、紧凑分隔符、UTF-8、禁止 NaN/Inf，再计算 SHA256。
时间戳、显示名等非执行字段放在外层，不改变同一执行快照的摘要。
仅记录“清单文件哈希相同”不够，执行前仍须验证程序、源码及资产本身与清单相符。

操作规则：

1. 预览计划不启动任何子进程，不创建 runs/ 真实任务目录。
2. 修改草稿会使旧 revision 的确认失效；旧 plan 对象继续留存但不能冒充最新计划。
3. 提交须同时匹配 plan_id、plan_digest 及草稿确认版本。
4. 任务一旦创建，其快照冻结；以后更改草稿不会改动运行参数。
5. 预览后程序或配置变化时，返回 PLAN_STALE，要求重新生成计划，不能静默使用新文件。

## 4. 服务接口草案

首版是进程内 Python 服务，不要求把下列方法实现为 HTTP API。
返回对象必须可序列化，后台模块不得返回 Streamlit 控件或工作器内部进程句柄。

| 方法 | 输入 | 输出 | 副作用 |
|---|---|---|---|
| create_conversation | 可选显示标题 | Conversation | 只创建产品元数据 |
| update_draft | conversation_id、文本/表单请求、expected_revision | Draft | 更新草稿，不执行 |
| preview_plan | draft_id、expected_revision | ExecutionPlan | 校验并冻结快照，不执行 |
| submit_plan | plan_id、plan_digest、request_id | JobReceipt | 明确提交后创建排队任务 |
| get_job_snapshot | job_id、可选 after_seq | JobSnapshot | 只读；可以返回较新的快照 |
| cancel_job | job_id、cancel_request_id | CancelReceipt | 请求取消，不表示已终止 |
| list_records | 状态/时间筛选、分页游标 | ArchivePage | 只读索引 |
| get_report | report_id、可选 case_id | ReportView | 只读适配，保留原结论 |
| get_log_tail | job_id、stream、cursor、limit | LogSlice | 读取绑定任务的日志片段 |
| export_report | report_id、格式、export_request_id | ExportArtifact | 仅在受控导出目录生成产物 |

get_job_snapshot 不得触发重启或新任务。
消息发送不等于 submit_plan；模型回复和页面重绘同样不等于提交。
只读报告接口不自动运行新验证器，也不重写历史结果。

## 5. 幂等与并发条件

- 相同 request_id + 相同计划返回同一 job_id，不重复启动。
- 相同 request_id + 不同计划返回 REQUEST_CONFLICT，不覆盖原任务。
- expected_revision 不符返回 DRAFT_CONFLICT，不把旧草稿覆盖新草稿。
- 产品层提交在同一个服务实例中串行登记；跨进程执行仍由统一租约保护。
- 提交索引、job 文件写入失败时不能返回“已接受”；保留可识别的未完成登记。
- 服务启动发现登记不完整时先对账，不能仅凭浏览器重连自动启动一次仿真。
- 不把 legacy CLI 重新输入一条命令当作浏览器重试；旧 CLI 明确调用有独立运行标识。

## 6. 统一快照

| 快照分区 | 关键字段 |
|---|---|
| context | conversation_id、draft_id、plan_id、job_id、report_id |
| selection | 当前 case_id、当前报告标签页 |
| data_source | view_mode、producer_kind、source_id、observed_at、completeness |
| execution | job_state、active_case_id、case_phase、cancel_requested、owner、timestamps、failure |
| progress | confirmed_frames、target_frames、confirmed_total、target_total、source_cursor |
| results | 现有 result_status、errors、warnings、checks_schema、checks |
| metrics | 可空值、单位、分母、数据完整性、来源路径 |
| logs | stdout/stderr 游标及片段 |

view_mode 为 empty、plan_preview、live、archive、synthetic；
producer_kind 为 simulation、synthetic、legacy_unknown，不能仅凭旧目录名猜测为真实采样。
旧记录没有新增字段时保留缺项标识，不补造标识或检查通过记录。

## 7. 右侧数据绑定规则

- 选中 case_id 必须属于当前选中 job/report。
- 新草稿生成后右侧默认切换到 plan_preview；不继续显示旧任务的成功标志和指标。
- 已启动的旧任务独立运行并可重新选中，不因草稿编辑自动取消。
- 用户主动查看历史时显示 archive 来源和旧任务标识，不把旧记录挂到当前草稿。
- 后台更新只有在 job_id 和视图上下文匹配时才刷新当前面板。
- 模型回复按 request_id 映射到草稿版本；过期回复不覆盖新草稿。

## 8. 文件与时间

BG-02 产品元数据当前集中在 data/planning/state.json，以一次原子写入保存对象与确认索引。
此前逐对象目录规划暂缓；BG-03 执行提交索引需保持原标识并设计登记恢复。
真实任务证据仍位于 runs；合成样例位于 tests/fixtures 或独立演示数据区。
统一保存 UTC ISO 时间戳，界面按明确的显示时区转换；本项目默认显示 Asia/Shanghai。
持续时间用单调时钟计算，不能以可能被校时的墙上时钟差作为精确持续时间。

## BG02 确认接口落地

create_conversation、update_draft、preview_plan 已实现。confirm_plan 只记录 plan-confirmation 命名空间的确认收据，返回 CONFIRMED_NOT_SUBMITTED，job_id 为空。
verify_confirmation 在执行前重新检查草稿与实际文件身份；submit_plan 与 execution-submit 幂等索引仍属 BG-03。
本轮真实验证通过实验脚本显式调用旧 runner.execute，并在独立协议中关联 report_id。
详见 [BG-02 实现与验证](BG02_实现与验证.md)。

## BG03 任务接口落地

JobManager已实现submit_plan(plan_id, digest, request_id, confirmation_id)、get_job_snapshot(job_id, after_seq=None)、cancel_job(job_id, cancel_request_id)。
执行提交使用execution-submit命名空间；提交索引与job-v1在同一planning-store-v1原子状态中发布。
事件暂嵌入任务events数组而不分拆JSONL。模型确认接口仍只确认，明确submit_plan才排队。
详见 [BG-03实现与验证](BG03_实现与验证.md)。

## BG04 界面接入

AppService封装预览、明确提交、查询、取消和归档；构造及读取页面不启动工作器。
同服务进程缓存一个实例，submit延迟创建JobManager，前端保留确认和执行请求标识供重试复用。
日志为只读尾部快照，增量游标待BG-05。见 [BG-04说明](BG04_实现与验证.md)。

## BG05 遥测落地

AppService.telemetry(job_id, cursors)返回job-telemetry-v1及按用例划分的下一游标；log_slice按任务、用例、stdout/stderr隔离。
游标只存调用方，不写原始证据或job状态。完整帧统计、ETA和实时视图均不产生最终判定。见 [说明](BG05_实现与验证.md)。

## BG06 导出接口

AppService.export_report(report_id, format, case_id=None)返回带来源摘要和SHA256的产物清单；export_content(artifact_id)在重新核对来源和文件后返回字节。
产物位于项目exports，使用benchagent-export-v1。PDF能力由当前渲染指纹验收门禁决定。见 [说明](BG06_实现与验证.md)。
