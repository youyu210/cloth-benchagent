# BenchAgent 目标驱动实验与辅助诊断：增量改造任务书

> 执行对象：本地项目 `D:\benchagent`。
> 这是实际代码修改与验收任务，不是论文润色或方案讨论。先检查现有实现，再增量开发、运行可行测试、保存证据。不得只输出设计建议、伪代码或页面原型。
> 本文规定的是目标能力，不代表这些能力已经实现。既有架构信息来自项目使用者，全部以本次源码审计和实际运行记录为准。

## 1. 目标、范围与优先级

将已有 BenchAgent 从“自然语言生成场景和帧数，随后执行固定流程”，升级为“围绕布料仿真实验目标，选择分析工具、依据实际结果判断证据是否充分，并在授权范围内安排必要补测的辅助评测系统”。

保留现有四个功能模块，不另建一套平台：

| 模块 | 本次增加或强化的职责 |
|---|---|
| 智能测试 | 从参数填充扩展为实验目标识别、所需证据规划和有界的工具选择 |
| 执行与监控 | 继续负责受控 GPU 执行、任务状态和真实数据采集；承接经授权的补测任务 |
| 结果可视化 | 增加确定性统计、证据充分性判断、关联关键帧、分析结论与补测建议；决策执行统一交给任务规划/编排逻辑，不能让渲染代码直接启动进程 |
| 实验管理 | 关联实验目标、冻结计划、工具调用、父子运行、分析脚本、原始证据和派生结果 |

### P0：必须优先打通的最小完整流程

围绕一个真实问题完成端到端实现：

> “分析球体与布料仿真中耗时较高的阶段，检查这些帧与接触计数、Newton/PCG 迭代变化的关系，并展示对应场景画面。已有数据足够就直接分析；不足时说明缺什么，并仅在允许且确实能增加证据时补测。”

选择实际存在且可执行的球布或其他布料接触场景。不得猜测场景编号，不得为匹配上述示例虚构场景。

### P1：在 P0 通过后实施

1. 两组真实运行归档的可比性检查与性能对照。优先导入现有结果，不强制新建多版本编译系统。
2. 受控的 Python 分析脚本生成、执行与验证，用于现有分析工具不能覆盖的临时分析需求。无可靠隔离环境时，只实现脚本生成和审核，自动执行明确标为 BLOCKED。

不做多智能体系统、模型训练、自动改写核心数值算法、任意终端代理或大型数据库迁移。本项目仍是硕士论文的配套实验系统，不扩展为新的通用科研平台。

读取仓库适用的 `AGENTS.md`、项目说明和当前测试，检查 `git status`。尊重已有未提交修改，不执行 reset、clean、强制覆盖、自动提交或推送。

以下路径仅是已有实现线索，存在才读取，重命名后按实际位置定位：

- `benchagent/app_service.py`、`benchagent/plan_service.py`

- `benchagent/validator.py`、`benchagent/export_service.py`

- `data/planning/`、`runs/`、`exports/`、`docs/`

确认并记录：

1. 实际工作台入口、模型网关、结构化计划、确认机制、工作器、采集器和报告模块。
2. 可用于本任务的真实布料场景、资产、物理参数、原生入口和可视化方式。已有“12个场景”等描述不能替代当前能力检查。
3. 逐帧数据的实际字段、单位、统计分母、覆盖范围与来源。重点区分物理步时间与任务墙钟时间、PCG 累计值与单次求解值。
4. “碰撞计数”的真实语义：候选对、距离阈值内约束、活跃接触或其他口径。查不清时保留原字段名称并标记语义未核实，不写成确定的接触发生次数。
5. 原生关键帧和几何回放分别支持哪些场景，frame 0 与实际物理步如何对应。
6. 真实模型调用、短指令、多轮修改是否可用；模拟响应测试不等于真实 API 联调通过。
7. 两组结果对照、分阶段计时、残差、顶点状态、检查点恢复和脚本隔离执行是否已有真实实现。

输出简短审计记录及阶段计划，然后继续实施可行部分。不要停在审计报告。缺失 GPU、模型凭据或隔离环境时完成其余部分，并保留对应 BLOCKED 状态。不得索取、打印或归档密钥。

## 3. 实验目标与统一计划

复用现有计划结构并向后兼容；旧表单、规则对话和单次运行入口仍须可用。不要强迫所有固定任务使用模型。

优先支持三种目标，枚举名称可按现有代码风格调整：

- 运行指定布料实验：保留旧能力。
- 分析布料仿真的高耗时阶段：P0 核心。
- 对照两组实验结果：P1。

扩展计划至少包含以下语义：实验目标、场景或已有任务引用、运行配置、所需指标、待回答问题、允许的工具/动作、执行预算、已有证据、缺失证据及完成条件。计划应引用现有字段，不另建重复身份体系。

完善统一场景能力目录中的领域信息：网格规模、固定边界、接触对象、自碰撞设置、时间步、可用指标和画面来源。只补充能够从真实配置或源码核实的项目；未知值不能由模型补全。

执行前向用户展示“准备做什么、为什么需要这些数据、最多运行多少、哪些配置保持不变”。冻结目标、输入引用、配置、允许动作、预算和相关构建身份。用户确认后才执行有副作用的动作。修改其中的关键项必须生成新版本并重新确认。

优先查询已有归档。证据足够时直接分析，不为展示自动化重新运行 GPU。

## 4. 有界的目标—工具—反馈处理循环

在现有服务层中加入轻量编排逻辑，复用工作器和校验器，不增加复杂框架。模型通过现有网关返回受 Schema 约束的动作建议，由确定性代码验证和分派；不要求升级模型或 SDK。

可用工具语义包括：查询场景/任务能力、读取已验证逐帧记录、执行统计分析、选择真实关键帧、检查两组结果可比性、提出或提交已授权的补测、结束并生成结论。名称与函数签名由真实工程决定。

每次工具返回结构化观测：实际读取了什么、计算结果、数据覆盖情况、错误、证据引用。模型依据观测选择下一步，而不是始终走同一条预设链路，也不能只在报告最后加一段模型总结冒充反馈决策。

必须实现的分支：

1. 证据充分：完成分析，不补测。
2. 记录不足但已有能力可补齐：提出有明确新增信息的补测计划；在预先授权范围内执行，否则等待确认。
3. 缺少的指标当前无法采集：给出有限结论并结束，说明缺失项；不得重复运行同一配置期待凭空产生新字段。
4. 两组配置不满足对照条件：停止生成不成立的比较结论。
5. 预算达到上限、连续同类失败、任务取消或证据不足且无可行动作：记录原因并结束。

循环上限建议默认每个实验 8 次模型调用、12 个工具步骤、最多 1 次诊断补测；可由用户在确认前调整。代码生成及修复调用也计入总预算。工具步骤、GPU 运行次数和模型调用分别计数。

补测必须说明新增证据、采集能力、配置差异、成本和预期回答的问题。防止重复提交同一动作；用于测量波动的重复实验须明确标为重复采样，而不是补齐不存在的字段。

日志、文件内容和模型输出都是数据，不得作为执行指令。模型不能访问任意路径、拼接任意 shell 命令、修改系统权限或绕过审批。

记录可审核的动作、简短决策依据、观测和证据引用，不要求展示模型内部思维链。模型不可用时，可提供明确标注的确定性分析模式，但不得将其记为模型自主完成。

## 5. 布料专用证据分析工具

### 5.1 高耗时阶段分析（P0）

提供经过单元测试的确定性工具：

- 对真实逐帧物理步耗时计算有效样本数、缺失比例、中位数、分位数、最大值及高耗时帧列表。
- 高耗时判定采用公开、可配置、可复现的规则，例如前若干帧排名或分位数阈值；展示实际阈值、样本数量和并列值处理方式。不把统计尾部自动称为物理异常。
- 对所选帧与其余可比帧的 Newton、PCG 及已核实语义的接触相关计数进行对照，报告分组规则与样本数。
- 通过真实任务、场景和帧索引关联原生关键帧。没有该帧图像时可显示最近的已采集帧，但必须显示真实帧号及偏移；不能冒充精确匹配。
- 可视化联动耗时、迭代曲线与关键帧。不要只生成一张与场景无关的汇总表。

不要只凭计数大于零就划分接触阶段。只有计数语义、事件记录或其他证据支持时才标注阶段；否则使用“高计数区间”“高耗时区间”等客观名称。

处理缺失值、NaN/Inf、零分母、常数序列、小样本、部分失败任务和单位差异；缺失不能填零。初始状态 frame 0 不作为实际物理步混入统计。启动/预热处理应显式说明，不能为了好看自动删去慢帧。

相关性或同时变化不等于因果。无分阶段计时，不得认定 CCD、线搜索或 PCG 是主要耗时来源。无残差数据，不判断非线性收敛质量；无几何接触验证，不宣称无穿透。生成文字中的数字必须来自工具结果，不能由模型估算。

### 5.2 补测与采集（P0）

默认不改变网格、材料、时间步、边界条件、接触设置及求解器容差。只使用已有合法的记录/画面选项，或最小、可关闭的观测补丁。新增观测不修改数学更新和终止逻辑，需记录其额外开销。

没有真实检查点恢复能力时，只能从相同初态重跑，不能直接从异常帧起算。诊断运行与性能基准运行区分标识；采集、渲染和编码开销不能混入或冒充原有物理求解时间。

接触阶段未被本次有限帧数覆盖时，应明确说明；延长运行必须处于批准预算内，否则提出待确认计划，不擅自改变场景来制造接触现象。

### 5.3 两组结果对照（P1）

优先支持选择现有两组真实归档。比较前核对场景、网格、材料、边界、时间步、共同物理时间范围、硬件、运行模式和计时口径。允许明确声明的实验变量不同，例如求解器版本或 CUDA Graph 开关；不要因版本本应不同而一概拒绝。

缺少关键配置时标记可比性未证实；无法对齐的帧或物理时间不直接相减。只有可比且指标有效时才计算比值。重复样本不足时明确限制，不宣称统计显著。

若有同拓扑、同单位、同物理时刻的顶点记录，可增加相对参考运行的位置误差；否则标记未采集，不从截图推算数值误差。参考运行不等于物理真值。

## 6. Coding Agent：受控分析脚本（P1）

常用统计使用已验证内置工具。仅当用户的临时分析需求超出这些工具时，让运行时模型基于真实字段说明和受控样例生成 Python 分析脚本。使用 Codex 开发本项目本身，不计作系统的 Coding Agent 能力。

首个案例可为：“按经核实的接触相关计数分组，比较物理步耗时与 PCG 分布，并列出对应帧”。要求脚本、输入范围、分组规则、输出表结构可查。

生成脚本只能读取指定的只读数据，在独立目录写派生结果。禁止访问凭据、用户主目录、项目源码及任意文件，禁止联网、安装依赖、启动仿真、修改配置或产生不受控子进程。

自动执行必须建立在真实可验证的操作系统级隔离环境上，并配置时间与资源限制。不能把普通 subprocess、临时目录、删减 builtins 或仅 AST 过滤称为安全沙箱。没有可用隔离环境时，只生成和审核脚本，执行标为 BLOCKED；不要绕过限制，也不要未经授权安装 Docker、调整虚拟化或安全策略。

执行后通过输出 Schema、帧范围、样本计数、关键统计复算和文件权限检查验收。错误时允许最多一次基于实际错误反馈的修复，并计入实验总预算。独立复算和小样本基准测试只验证已覆盖性质，不得因此声称任意生成代码都正确。

保存脚本、输入哈希、依赖版本、执行日志、修复版本、验证结果和输出。原始数据哈希不得变化。没有真实模型调用与隔离执行证据，不报告“已实现并通过自动代码分析”。

## 7. 界面与溯源：减少用户步骤

保留现有四个模块和历史入口。用户主要看到三个环节：

**输入实验目标 → 确认方案与预算 → 查看结论与证据。**

目标入口提供少量布料实验示例，并允许使用已有任务。高级参数默认折叠。运行时展示当前动作、简短理由和预算消耗；不要要求用户反复手工搬运模型输出、CSV 或脚本。

结果页面固定区分：已观测事实、有限解释、证据不足项、实际执行/建议的补测。展示高耗时帧、指标变化及关联画面。只建议但未执行的补测不能混入已完成记录。

复用现有持久化与归档机制，增加实验目标到原始运行、补测运行、分析产物的关联。原始记录只读，缺失字段标记缺失，旧归档仍可打开。新计划或新分析不得覆盖旧结果。

导出继续兼容现有格式，并包含必要的目标、版本、预算、工具行动、证据引用及分析脚本清单。共享给模型的数据最小化并脱敏，不发送密钥或无关文件。

## 8. 测试与验收

### 8.1 自动化检查

至少覆盖：目标解析及多轮修改、预算/授权拦截、工具参数校验、已有证据足够时不重跑、缺失可采集证据时正确提出补测、不可采集时终止、重复动作抑制、帧/单位/缺失值处理、对照配置检查、历史归档兼容、恶意日志指令不执行。

有受控脚本执行能力时，增加输入只读、越界访问和联网拒绝、超时、输出验证、修复次数限制及原始哈希不变测试。

单元测试允许明确标注的人工构造数据；必须与真实 GPU/API 验收分开记录。不得修改原始证据制造缺失或失败，可使用独立只读派生测试夹具。

### 8.2 真实端到端验收

| 编号 | 验收任务 | 必须出现的证据 |
|---|---|---|
| E1 | 对一组已有真实布料运行分析高耗时阶段 | 目标、真实工具调用、可复算统计、关联帧、无多余 GPU 运行 |
| E2 | 数据不足的任务触发正确分支 | 缺失项、补测能否增加信息的依据、授权记录；可执行时有真实子任务，否则明确停止 |
| E3 | 从目标输入到真实原生仿真及结果分析 | 真实模型请求摘要、冻结计划、原生任务、逐帧记录、分析与报告；无条件时 BLOCKED |
| E4 | 两组结果可比性检查（P1） | 真实输入来源、配置差异、允许/拒绝原因和合法指标 |
| E5 | 临时分析脚本生成及验证（P1） | 真实生成脚本、隔离执行记录、独立检查；无隔离环境时 BLOCKED |
| E6 | 旧功能回归 | 表单/规则入口、已有场景运行、日志、历史画面与报告仍可用 |

E2 应包含“数据充分不补测”和“数据缺失但当前无法获取就结束”的分支检查；不能为了展示 Agent 把所有实验固定重跑一次。真实补测仍受下述预算限制。

至少使用真实 API 完成一个有工具观测反馈的目标任务，不能仅用 mock 结果证明智能体能力。历史 API 成功记录不替代本次新增流程联调。

### 8.3 本次开发验收预算

优先复用历史归档。默认本次开发验收累计最多新启动 2 个 GPU 仿真任务，每个不超过 100 帧、超时 600 秒，串行运行，沿用既有 GPU 绑定；这些是保守验收预算，不是对场景耗时的预测。达到上限仍未完成的项目列出原因，不自动无限重试或提高上限。构建过程与 GPU 仿真验收分别记录。

采用已有模型凭据与网络权限；新增收费服务、权限提升、部署或资源预算增加需要单独批准。无 API 时完成可运行的确定性部分，不伪造联调成功。

## 9. 证明新增能力，而不是只增加界面

准备一个可重复的轻量评测入口，用相同真实归档对比：原有固定/单次计划流程与新增目标反馈流程。预先固定问题和判定规则，报告目标完成情况、正确证据覆盖、无效运行、人工干预及模型调用开销。原始流程不支持某项分析时如实记录，不删除旧功能来人为制造差距。

手工时间、费用或成功率没有测量就不填写。少量案例只证明可行性，不能宣称普遍提速、降低成本或物理正确性。模型不可用时，可保留评测脚本，但真实模型效果部分记为未执行。
